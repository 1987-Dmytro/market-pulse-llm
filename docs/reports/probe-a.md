## 1. D1 ($0) — `reader_thread_gm4`, registered before anything could serve it

`4cbbd24 feat(probe-a D1): the thread reader, registered before anything can serve it`

The prompt joins the fifteen already in `prompts.PROMPTS` with its own sha
`b272115637f784ad…` (`prompts.prompt_sha256("reader_thread_gm4")`, pinned in the registration). Built from
the design authority and not from taste:

- **Frame** — PRODUCT.md's seven director questions, spelled out in the prompt: a signal is only
  what answers one of them, and a thread that carries none is a normal answer with an empty list.
  (Seven, not the heading's six — the table gained question 7 on 2026-08-10. Dv390.)
- **Duties in order** (plan §2 C, the operator's clarification of 15.08) — (1) the thread, the post
  sets the topic; (2) every trade mark and chain name resolved from its context, one phrase and the
  quote it was read in; (3) only then signals. Written as three numbered duties with «never begin
  one before the one above it is finished», because the failure it guards is the one the manual
  reading did not make: a signal attached to a name nobody resolved.
- **Taxonomy exactly as ratified 15.08** — `молочный_бренд · сеть_ритейлер · категория_личное ·
  не_наш_рынок`, `спрос · жалоба · похвала · привычка · тренд` (open, with `proposed: true` as its
  only escape), `плюс_спам · скам · оффтоп`. Russian tokens inside an English prompt on purpose:
  they are the operator's ratified words, and translating them would make the prompt, the parser and
  the sitting three different taxonomies.
- **Aspects and stances are the repo's own** — `scorer.INTENTS_V2` (taste · price · packaging ·
  quality · availability · service) and `SENTIMENT_LABELS`. Not a choice: PRODUCT.md question 2
  answers itself with exactly those six words in Russian, and plan §3's last paragraph requires the
  stance layer to be comparable with the heads the model already has — «расхождения двух слоёв —
  отдельная колонка честности» is impossible between two vocabularies.
- **The four entity cases of plan §5 (4) are deliberately absent from the text.** They are the bar.
  What the prompt carries is the law they were ruled from, including «a word that is both a name and
  an ordinary word of the language is a name only where the text uses it as one» — the rule the
  reader has to apply on its own.
- **No shape line and no worked example**, unlike the position prompts: every object's keys are
  spelled out inline, so an illustration would add only values to copy.

**One parser, in `prompts.py`, as the contract asks.** `parse_reply` gains a `reader_thread_gm4`
branch after `_object` (which already unwraps a fence and reads from the first brace); the positions
prompts stay refused by name because their parser validates a tier ladder that means nothing here.
The branch is strict about DOMAINS and silent about consistency: a `subject_type` outside the
taxonomy is an answer nothing downstream can read, while a comment appearing in both `per_comment`
and `noise` is a bookkeeping slip whose two rows are each readable — and a refusal costs the whole
thread, which the probe pays for once. `stance` and `subject_id` are optional-and-nullable because
plan §3's own second signal carries neither, and an absent key read as `null` says «not stated»,
which is a different answer from «neutral».

| input | 40 000 chars, LOUD refusal | the largest of the 111 threads renders to **27 593** chars (125 payable comments, @matusi_ukr #22058; 10 784 input tokens) through this very function; median 6 095. The guard sits ~45% above the measured maximum so it cannot fire on a thread the probe is registered to read |
| output | 2 000 tokens | arithmetic on the pinned tokenizer, part by part: thread block + both summaries 98 tokens, an entity 63, a signal with its quote 103, a `per_comment` row 47, a noise row 22. The output ceiling does **not** cover the three threads above a hundred payable comments (125, 108,

## 5. The paid pass — stopped before it was opened

### 5.1 What the cap buys, in seconds

The only rate this repo owns for this endpoint class is measured:
`results/run_5c2_comments.json :: rate_usd_per_second = 0.00030669` ($1.104/h).

```
$0.20 ÷ $0.00030669/s = 652.1 s of billed worker time — all in, everything included
```

### 5.2 What the registered run needs, at the census's own most optimistic end

`results/gate_census_w1.json` prices the cell as an INTERVAL because a thread call is a different
job from a comment call. Its **lower** end assumes a thread call costs exactly what one comment call
cost (4.247 s):

| item | seconds | usd | source |
|---|---|---|---|
| 111 threads at the census's lower bound | 471.4 | 0.1446 | `gate_census_w1.json :: grid.narrow\|silencers_on.cost.lower_usd` |
| one worker weight load, measured | 99 | 0.0304 | `spend_5c1_vis.json` — vis-b's worker loaded 1 188 shards in 99 s |
| **endpoint subtotal** | **570.4** | **0.1749** | |
| a staging pod, 8 min at today's cheapest EU-RO-1 class ($0.240/h) | — | 0.0320 | `runpodctl gpu list`, RTX 2000 Ada, stock Low |
| **total** | | **$0.2069** | **> $0.20** |

That is before the warm-up, before the handshake, before the 60 s idle timeout, and before a second
boot — and vis-b's measured setup rung, which is the same manoeuvre this contract needs, cost
**$0.1581** on its own with zero output (two staging pods, an endpoint, two weight loads, two
refused handshakes).

### 5.3 And the optimistic end is not reachable

The census's lower bound assumes a thread call costs one comment call. Measured on the pinned
tokenizer, on this window's own rows:

| | comment call (5c2, n=400) | reader call (the 111) |
|---|---|---|
| input tokens, median | **809** | **1 717** |
| input tokens, max | 1 060 | 10 784 |
| output ceiling | 256 | **2 000** |

2.1× the input and 7.8× the ceiling. The true cost sits above the lower bound, and the interval's
other end is $1.1879.

### 5.4 Why the staging pod cannot be skipped

The worker executes `/runpod-volume/repo`, and `reader_thread_gm4`, `ReaderClient` and the READER
branch of `settings()` did not exist anywhere before today's commits. A running worker holds the
code it booted with — `serverless update` does not restart it and only `serverless delete` stops it
(hot.md, vis-b, $0.1581) — so the volume must be staged **before** the endpoint exists, from a pod,
on a second meter.

### 5.5 The decision, and what was NOT done

Nothing was created. The read-only inventory taken before the arithmetic is the baseline and is
still true:

```
$ runpodctl serverless list   → []
$ runpodctl pod list -a       → []
$ runpodctl network-volume list → [ { "id": "qw4nwleanc", "name": "mp-srv2", "size": 100, "dataCenterId": "EU-RO-1" } ]
```

**Spend this session: $0.00.** The contract's own money discipline is «Do not exceed $0.20 all-in»,
and a run whose measured floor is $0.2069 cannot be opened under it. Buying only the setup and the
warm-up — ~$0.09–0.16 — would spend ~80% of the cap to watch a STOP that §5.1–5.3 already determine,
and it would do it by creating a billing resource whose known failure mode (vis-b's: two boots, a
refused handshake) lands on the ceiling the contract forbids crossing. The go/no-go exists to decide
a cost that is unknown between two bounds; this one is decided from the other side, by division.

   once — came from enumerating what the census had only counted, and every one of them would
   otherwise have surfaced as a bar failing after the money was spent.
3. **A prompt registry is a pinned artefact.** Adding one prompt reddened five tests across three
   records that have nothing to do with prompts. The house manoeuvre exists and worked, but the cost
   of a fifth instrument is now visibly three pin decisions, not one edit.
4. **The preflight earns its keep on the template, not on the guards.** Nine of its ten new checks
   are pure and could have run anywhere; the tenth — that Gemma 4's own template at the pinned
   revision opens with `<bos>` and closes the thought channel on THIS request — is the one that
   could only be bought here, and it is the one that would have cost a boot to discover.
