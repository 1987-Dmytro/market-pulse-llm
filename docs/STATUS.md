## Что это за проект (одним абзацем)

Ключевой инструмент маркетинговых исследований компании (ТМ «Гармонія»):
мониторим Telegram-каналы украинских ритейл-сетей (Сільпо, АТБ, Varus) и
агрегаторов, находим анонсы новинок и промо по молочке/мороженому, извлекаем
бренды, классифицируем реакции покупателей (тональность, сарказм, скрытые
интенции: вкус/цена/упаковка/качество/наличие). Ядро — одна открытая LLM,
дообученная QLoRA на арендованной GPU. MVP: только Telegram, $0 за данные.

## Решения, которые СОЗНАТЕЛЬНО ОТЛОЖЕНЫ (и когда принимаются)

- **Какую LLM дообучаем** — по-прежнему открыто, но **числа теперь есть**
  (таблица в «Итог 3b»). Исполнитель выводов о выборе не делает: решение
  на гейте Phase 4, совместно. Пока модель не выбрана, **у G1d и G1e нет
  якоря** — якорь это строка выбранной базовой модели, а не лучшая из трёх
  (ADR `3b-infra-and-precision` §(f)).
- ~~GPU-провайдер~~ РЕШЕНО 2026-07-28, УТОЧНЕНО 2026-07-31: **RunPod** остаётся
  провайдером для **обучения** (Phase 4 QLoRA) — A6000 48GB $0.53/ч, network
  volume $0.07/ГБ/мес, есть CLI `runpodctl` v2. Но **бейзлайны 3b на нём не
  считаются**: zero-shot ушёл на API OpenRouter (см. ревизию 31.07).
  Пополнение RunPod отложено до гейта Phase 4 — решение оператора 31.07.
- ~~Архитектура продакшн-петли~~ РЕШЕНО на архитектурной сессии 2026-07-28:
  инференс — RunPod serverless (батч 2–4×/день, ~$2–5/мес); петля сбора —
  Mac cron для MVP, VPS (~$5/мес) при переходе в бой (Phase 5); агрегаты —
  SQLite; дашборд — Streamlit. Каждый блок заменяем независимо.
- Бейзлайны Phase 3 расширены: + справочная строка zero-shot фронтирного API
  (Claude Haiku, ~$1–3 одноразово) — «самая дешёвая реалистичная
  альтернатива». Гейты G1a–e остаются привязаны к трём основным бейзлайнам.
- ~~Список моделей-кандидатов~~ РЕШЕНО 2026-07-31 живым поиском: три кандидата
  зафиксированы (см. ревизию инфраструктуры ниже), исполнитель их не меняет.
- **LoRA в bf16 или QLoRA в 4-bit** — новое отложенное решение, поднято
  оператором 2026-07-31, принимается на гейте Phase 4 вместе с выбором модели.
  Суть: «Q» в QLoRA — это только квантование замороженной базы; обычная LoRA
  на неквантованной bf16-базе технически возможна и упирается лишь в память.
  Расклад по кандидатам (база + адаптеры + активации):
  Gemma-4-31B — bf16 ~70 ГБ / 4-bit ~24 ГБ · Qwen3.6-27B — ~62 / ~21 ·
  **Qwen3.5-9B — ~22 / ~8, то есть bf16 влезает в A6000 48 ГБ.**
  Цена обучения аргументом НЕ является: датасет крошечный (2350 реальных +
  600 синтетических строк, короткие тексты), прогон 1–1.5 ч, разница
  QLoRA на A6000 ($0.53/ч) против LoRA bf16 на A100-80 ($1.39/ч) — единицы
  долларов. Решает согласованность: **учим в той точности, в которой отдаём
  в прод**. Адаптер, обученный на квантованной базе и влитый в bf16-веса,
  расходится с ними — и ровно так же расходится адаптер, обученный на bf16
  и запущенный на квантованной базе. Прод по решению 28.07 — RunPod
  serverless, батч 2–4×/день, где холодный старт (вес модели) важнее
  вычислений, что склоняет к квантованию для 27B/31B.
  Три ветки: (1) выигрывает 9B → чистая LoRA bf16 на A6000, квантования нет
  нигде; (2) выигрывает 27B/31B и прод квантованный → QLoRA; (3) выигрывает
  27B/31B и прод bf16 → LoRA bf16 на A100-80.

## Ревизия инфраструктуры (2026-07-31)

Повод: у оператора пополнен **OpenRouter ($9.84)**, а на **RunPod $0.00**.
Это сломало предпосылку замороженного промта 3b («аренда A6000, bf16»)
и мы пересобрали шаг на совместном разборе.

**Что решено:**

1. **Zero-shot считаем через API OpenRouter, GPU в 3b не арендуем.**
   758 строк на кандидата (400 комментов + 250 постов + 108 холдаута)
   стоят ~$0.05–0.25 за модель. Весь шаг ≈ $2 против ~$12 аренды.
   Потолок бюджета: **$8** (pre-registered, ниже реального баланса).
2. **Правило точности (precision) — записано ДО первых цифр.**
   Исполнитель сначала опрашивает `/api/v1/models/<slug>/endpoints` по всем
   трём кандидатам. Если `bf16` доступен у всех троих — берём bf16 (исходное
   ограничение 28.07 соблюдено). Если хоть у одного нет — берём `fp8` у всех
   троих. **Смешивать точности между кандидатами запрещено** — иначе разница
   в числах будет от квантизации, а не от модели, и парное сравнение
   рассыплется. Маршрутизация пиннится жёстко (`allow_fallbacks: false`),
   провайдер и квантизация пишутся в provenance каждой строки.
3. **Честная оговорка и её компенсация.** Числа приходят со сторонних
   эндпоинтов, а не с нашего железа. Компенсация: модель, выбранная на гейте
   Phase 4, один раз перепрогоняется zero-shot на нашем поде в смоуке —
   сверка «OpenRouter vs своё железо». Записано в ADR.
4. **Три кандидата зафиксированы оператором** (живой поиск проведён 31.07):
   `google/gemma-4-31b-it` (~31B, **Apache-2.0** — проверено по карточке HF
   и по странице лицензии Google, Gemma 4 сменила лицензионное семейство;
   в промте 3b было «Gemma Terms of Use») ·
   `qwen/qwen3.6-27b` (~27B, Apache-2.0) ·
   `qwen/qwen3.5-9b` (~9B, Apache-2.0 — дешёвая нижняя граница, отвечает на
   вопрос «а хватит ли маленькой»). Обе крупные вышли в апреле 2026.
5. **Справочная строка Haiku идёт через тот же OpenRouter** — отдельный ключ
   Anthropic не нужен, из `.env` он выпадает. Но **не** `:batch`: OpenRouter
   отдаёт этот вариант только через асинхронный `/api/beta/batches` и на
   `/chat/completions` возвращает 404. Прогнано на синхронном
   `anthropic/claude-haiku-4.5` ($1.00/$5.00 за 1M) — та же модель, +$0.24.
6. **XLM-R (supervised бейзлайн) обучаем локально на Mac (MPS), $0.**
   Сначала таймленный смоук; если оценка полного прогона > 60 минут —
   исполнитель останавливается и докладывает, переносим на под.
   **Сработало именно так:** смоук намерил 3.503 с/шаг на CPU (→ 130.8 мин)
   и 48.117 с/шаг на MPS (→ 1764 мин), оба выше потолка, полный прогон не
   стартовал. MPS на этой машине не просто медленнее — он ещё и падает по
   памяти на 9.07 ГиБ. Скрипт готов и ждёт пода.
7. **RunPod не пополняем сейчас.** Сейчас — только поставить `runpodctl`
   и создать API-ключ (бесплатно). Деньги (~$30–40) — на гейте Phase 4,
   когда известна модель. Важно на будущее: при балансе $0 поды **без**
   network volume удаляются безвозвратно, поды **с** volume — сохраняются.

## Итог 3b (2026-07-31, исполнитель отчитался)

**Правило precision сработало в ветку `fp8`:** у `qwen/qwen3.6-27b` нет ни
одного bf16-эндпоинта ни у одного провайдера, значит по предрегистрированному
правилу fp8 у всех троих. Пины: gemma → `parasail/fp8`, qwen3.6 → `io-net/fp8`,
qwen3.5 → `venice/fp8`, `allow_fallbacks: false`, квантизация и провайдер — в
provenance каждой строки. Probe воспроизводится командой
`python3 scripts/eval_zero_shot.py --precision-probe` (бесплатно, только GET).

Числа читаются `python3 scripts/show_results.py --last`. **Выводы о выборе
модели тут не делаются** — это гейт Phase 4.

Справочная строка в файле помечена так, что поиск по `G1d` её не найдёт: у неё
все поля `gate` переписаны в `ref`. Она не якорит гейты по решению 28.07.

**⚠️ qwen3.6-27b: два прогона, оба `gate_anchor_valid: false`.** Модель
возвращает JSON без поля `sentiment`. Первый прогон — 10 непригодных строк из
758, перезапуск 31.07 — 8. Строки в основном **те же самые** (3 из 4 на
комментах, 3 из 5 на холдауте совпали), то есть это свойство конкретных
текстов, а не сетевой шум; повторный прогон проблему не лечит. Порог 2%
превышен на холдауте (4 из 108 = 3.7%). Непригодные строки посчитаны отдельно
по причинам, названы по id и **исключены из счёта, а не подставлены дефолтной
меткой**.

Побочный результат перезапуска, который стоит держать в голове: **G1d у
qwen3.6 сдвинулся с 0.7308 на 0.7605 просто от другого подмножества строк.**
Это ровно то, о чём предупреждает оговорка про сторонние эндпоинты —
детерминизм на стороне провайдера не гарантирован даже при temperature 0.

**Три строки кандидатов не спарены по инстансам:** gemma и qwen3.5 посчитаны на
400/250/108, qwen3.6 — на 397/249/104. SPEC §5 требует «paired on identical
instances». Пересчёт по пересечению воспроизводим без единого нового запроса:
в каждой записи лежит `config.scored_ids_sha256` по каждому входу.

**Бюджет: $0.9124 из $8.00.** Провайдерская цифра, ledger — в
`results/spend_3b.json`. На ключе остаётся ~$9.09.

**Отклонения исполнителя от промта 3b** — девять штук, все в
`implementation-notes.md` § Deviations. Существенные: лицензия Gemma 4
оказалась Apache-2.0 (D3); `GET /api/v1/generation?id=` из промта не работает —
404 на валидный id при любой задержке, спенд считается из `usage.cost` в теле
ответа плюс сверка с `/credits` (D1); «errs on N of 108» отдано **тремя**
числами вместо одного, потому что поправка 3.2 говорит «misclassifies», а
холдаут несёт две метки — выбор чтения оставлен оператору (D2); дефолт XLM-R
переключён с MPS на CPU по измерениям (D7).

## ТЫ ЗДЕСЬ — что делать прямо сейчас (2026-07-31, после 3b)

Zero-shot половина 3b закрыта, отчёт исполнителя принят к разбору. Открыто
четыре вопроса, все — операторские, ни один исполнитель за вас не решил:

1. **Гейт выбора модели Phase 4** — по таблице «Итог 3b», совместно.
   Помнить: пока модель не выбрана, у G1d и G1e нет якоря.
2. **Что делать с qwen3.6-27b.** Перезапуск проведён и проблему не вылечил.
   Варианты: (а) считать строку годной с оговоркой и n на 4 меньше;
   (б) пересчитать все строки по пересечению id (бесплатно, из
   `scored_ids_sha256`); (в) исключить кандидата из сравнения. Выбор ваш.
3. **Какое чтение «misclassifies» определяет срез G1b** — ошибки по
   sentiment, по sarcasm или их объединение. Все три числа лежат в каждой
   записи.
4. **XLM-R: под или поднятый потолок.** 130.8 мин на CPU — это пол оценки, не
   точка. Исполнитель сознательно НЕ стал резать эпохи, укорачивать
   `MAX_LENGTH` или переписывать на общий энкодер — это подгонка
   предрегистрированного бейзлайна под часы, и решение ваше.

Дальше: пополнение RunPod ~$30–40 → брифинг Phase 4 (QLoRA: смоук → полный,
абляция синтетики, одна попытка). Выбранная модель должна получить **один
zero-shot перепрогон на нашем поде в смоуке Phase 4** — сверка «OpenRouter vs
своё железо», записана в ADR.
