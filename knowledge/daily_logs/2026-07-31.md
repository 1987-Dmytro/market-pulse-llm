## Decisions

**[[3b-infra-and-precision]] — 3b runs on OpenRouter at a pinned precision, not on a rented GPU.**
The premise of `docs/PROMPT-3b.md` rev. 1 evaporated: the operator funded **OpenRouter ($9.84)**
and left **RunPod at $0.00**, the opposite of the 2026-07-28 pre-flight. Zero-shot needs no GPU —
758 rows per candidate is ~$2 of tokens against ~$12 of A6000 rental, most of it idle while four
models load in turn. Cap set at **$8**, deliberately below the balance. No Anthropic key anywhere:
the reference row goes through the same vendor. [[gpu-provider-runpod]] was **amended, not
overturned** — RunPod stays the Phase 4 *training* provider and its top-up is deferred to the
Phase 4 gate.

**The precision constraint was rewritten as a rule before any number existed.** Rev. 1
pre-registered the *value* "bf16", which is unreachable on third-party endpoints. The replacement:
probe all three candidates' endpoints first; bf16 if all three offer it, otherwise fp8 for all
three, never mixed, never a silent fallback. It **fired into fp8** — `qwen/qwen3.6-27b` has no
bf16 endpoint at any provider. Pins `parasail/fp8`, `io-net/fp8`, `venice/fp8`,
`allow_fallbacks: false`, re-verified at every run start; the probe is a command
(`--precision-probe`), not a one-off. The honest caveat is paid off rather than waved away: the
chosen model owes **one zero-shot re-run on our own pod during the Phase 4 smoke**.

**[[phase4-base-model-gate]] — base model = `google/gemma-4-31b-it`; the unpaired 27B row cannot
flip it.** Four decisions at the evening gate review:

1. **Gemma-4-31B** leads every gated head among the candidates and leads the Haiku reference row
   on four of five cells (Haiku takes G1a `ru` by 0.0300; a reference row never anchors a gate).
   Clean run, no lost rows, Apache-2.0.
2. **The unpairedness is closed by a bound analysis at $0**, and every head survived it. Worst
   case is Gemma being *perfect* on the eight instances the 27B dropped, since dropping a row it
   got wrong would only raise its score; removing one correct row of class `L` moves that class
   alone by `2(1−F1_L)/(S−2)`, which `TP ≥ 1` caps at `2/S`. Bound vs gap: G1a `ua`
   0.0186 / 0.0421 · G1a `ru` **0** / 0.0021 (no `ru` row dropped — that cell was already paired)
   · G1c 0.0087 / 0.0376 · G1d 0.0037 / 0.1293 · G1e **0** / 0.0292 (the dropped post carries no
   gold brand). The ~$0.90 paired re-run held in reserve stayed unspent; the 27B rows keep
   `gate_anchor_valid: false` permanently.
3. **The G1b slice = the UNION** of sentiment and sarcasm errors — the reading
   [[3b-infra-and-precision]] §(e) deliberately refused to pick — and it is **defined by the
   chosen model's re-run on our own pod**, all 108 rows, per-row outputs persisted. OpenRouter's
   40/108 is a preview, not the slice.
4. **XLM-R runs overnight on this Mac's CPU**, the 60-minute ceiling lifted by the operator, with
   epochs / `MAX_LENGTH` / architecture untouched.

**A new Phase-4 fork, raised by the operator: plain LoRA vs 4-bit QLoRA.** Asking "can we adapt
the unquantized base?", the operator independently arrived at plain LoRA — the "Q" is only the
quantization of the frozen base. VRAM: Gemma-4-31B ~70 GB bf16 / ~24 GB 4-bit · Qwen3.6-27B
~62 / ~21 · Qwen3.5-9B ~22 / ~8, so bf16 fits a 48 GB A6000 only for the small one. **Training
cost is explicitly disqualified as the deciding argument** (~2 950 short rows, 1–1.5 h, single
dollars apart). The criterion is **train in the precision you serve**, as a distance scale:
bf16 → fp8 is a short hop, bf16 → 4-bit is far enough that the adapter must be trained against
the quantized base. Since Gemma-4-31B won, the working hypothesis is **branch (2), 4-bit QLoRA on
an A6000** — confirmed at the Phase 4 briefing, not before.

## What was built and measured

**Four zero-shot rows, 3 790 requests.** gemma-4-31b-it G1a 0.8944 · G1c 0.7981 · G1d 0.8898 ·
G1e 0.9211 · holdout errs 10/40. qwen3.6-27b 0.8541 / 0.7606 / 0.7605 / 0.8919 · 14/64.
qwen3.5-9b 0.7745 / 0.6252 / 0.5077 / 0.6476 · 26/70. Reference `claude-haiku-4.5` 0.8708 /
0.7739 / 0.7718 / 0.8537 · 21/47, written so a lookup for `G1d` cannot find it.

**Three findings that cost nothing today and would have cost a lot later.** Gemma 4 is
**Apache-2.0**, not the Gemma Terms of Use the candidate list assumed. `GET /api/v1/generation?id=`
— the spend-tracking mechanism the prompt named — **404s** for valid ids at every delay tried, so
spend reads `usage.cost` and reconciles against `/credits`. `claude-haiku-4.5:batch` is served only
through `/api/beta/batches`; the reference row ran on the synchronous slug for +$0.24 rather than
growing an async code path.

**The 2% guard earned its place twice.** qwen3.5-9b's first run lost 11 rows to HTTP 429 from a
pinned endpoint — fresh ids each time, a transport problem, and four workers plus six retries
fixed it. qwen3.6-27b returned JSON with no `sentiment` field, and the operator's re-run **did not
close it**: 8 unusable rows instead of 10, and **largely the same rows** (3 of 4 comment ids, 3 of
5 holdout ids) — the model on those texts, not noise. The same re-run priced the determinism
caveat: G1d moved **0.7308 → 0.7605** with commit, prompt hash, pin, temperature and seed all
identical. That 0.0298 swing is **14× the `ru` margin** the selection shows on one cell, which is
why the own-pod cross-check is an obligation.

**The defect the acceptance found, and its forward fix.** The 3b report and
`implementation-notes.md` claimed a paired re-score was "reproducible from the file, without
re-spending". It is not: records carry `scored_ids_sha256` (a *hash* of the id list) and error
counts, never the per-row predictions, so no metric can be recomputed on any subset. The original
sentence was restored **verbatim** (a `/save` edit had rewritten it away) with a dated correction
subsection under it. From step 3c every real run writes
`results/predictions/<slug>--<ts>.jsonl` — input, id, predicted labels, no gold and no source text
— plus `predictions_path` / `predictions_sha256`. Lines sort by `(input, id)`: at four workers a
hash of completion order is not a hash of the data. Six offline tests, the strongest of which
rebuilds `scored_ids_sha256` from the dump. **The six existing 3b runs get no backfill** — they
cannot be reconstructed and a synthesized dump would be worse than the gap.

**Two reporting bugs, both found by the operator asking "I don't understand" rather than by an
audit.** XLM-R is a classifier and cannot do G1e span extraction, so its blank cell would read as
"scored badly"; it now says **NOT COVERED** explicitly. And an adapter trained against a 4-bit base
compensates *that base's* quantization error, so merging it into bf16 weights corrects errors that
are no longer there — recorded as a Phase-5 footgun, with the rule that the artefact is scored in
the exact configuration that will serve production.

**Thirteen deviations logged for 3b/3c** in `implementation-notes.md` (D1–D9, E1–E4), each cited by
number, plus **F1–F3** for the ownership layer. The sharpest is **E1**: the runbook's full-run
command would have refused to train. The operator lifted *their* 60-minute ceiling, but the ceiling
also lives in code (`train_xlmr_baseline.py:307` prints the projection and exits 3), so the launch
adds `--time-budget-min 600`. Verbatim, the overnight job would have finished in forty seconds and
trained nothing.

the success line alone is silent through one — the terminal verdict came from the process
disappearing, then split into DONE or DIED by whether `wrote results/baselines.json` is in the log.

### The ownership layer, and the deny rules proved in combat

`2b423c8` installs the layer decided at the 3b close: three deny rules in `.claude/settings.json`,
one negative line appended to `/save` and `/close`, a four-line File-ownership matrix in
`CLAUDE.md` (94 lines, ceiling 200), and F1–F3 in `implementation-notes.md`. The `permissions`
block was inserted **before** `hooks`, so the diff is a pure insertion with zero `-` lines — a
mechanical proof that the hooks block is byte-identical rather than an eyeballed one.

**F1 — the rule form is `Edit(...)` only, and that is not a shortcut.** On Claude Code 2.1.220 a
`Write(path)` rule is accepted, **never consulted**, and prints a startup warning; an `Edit(path)`
rule covers every file-editing tool. A bare tool-level `Write` deny would have blocked writes to
executor files too. The anchor is `/docs/…` (project root, per the settings source), not
`docs/…` (cwd), so a session started in a subdirectory is still covered.

**Proved by refusal, with a negative control.** `Edit` on `docs/STATUS.md`, `docs/SPEC.md` and
`docs/PROMPT-3c.md` were all refused — the rules were live **without a restart** — while the
identical attempt on `docs/WATCHLIST.md` reached the tool and failed on content, so `docs/` as a
whole is still writable. Without that control, the refusal wording ("File is in a directory that
is denied") would have left a directory-wide block indistinguishable from the intended file-scoped
one. A **`Write`-tool probe on `docs/STATUS.md` was refused as well** (team lead's request at the
close), which is F1's claim confirmed from the other side. `git status` shows no modification
under `docs/` from any of it.
